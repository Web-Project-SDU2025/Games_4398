# 游戏管理数据库

项目使用课程分配的数据库 `java_1_02`。前后端在本地运行，数据库位于线上，连接沿用现有配置。

`../web-db.sql` 是迁移后的数据库导出文件，包含当前表结构、账号和菜单。开发者导入前需要选中目标数据库。

完整导出文件和 `backups/` 保存在本机。公开仓库中的 `schema.sql` 提供空表结构，`seed.sql` 提供角色和菜单。这两个文件用于初始化新建的空数据库；在已有库中重复导入会影响现有数据。

`backups/before_game_migration.sql` 保存修改前的完整数据库和示例数据，用于恢复旧版本。当前程序使用前述结构与初始化文件。

开发者已在当前在线数据库执行过一次 `migrate_game.sql`。该脚本会删除旧表的示例数据和字段，只适用于已备份的旧结构，当前数据库应保留已完成的迁移结果。

| 表 | 内容 |
| --- | --- |
| user | 登录账号、密码、角色、个人资料、头像、签名以及游戏关联 |
| user_type | 管理员和游戏用户两种角色 |
| game | 全站游戏信息 |
| user_game | 每个账户的游戏库 |
| game_favorite | 每个账户的收藏 |
| game_record | 每次游玩的分数、时长和时间 |
| blockcoin_wallet | 当前账户的字块币余额 |
| blockcoin_entry | 初始发放、购买、奖励与管理员调整的唯一业务流水 |
| reward_run | 正式关卡尝试、挑战码与已领取状态 |
| game_play | 通用游戏会话、有效时长、关卡结果与已发奖励 |
| game_revocation | 管理员游戏撤回、操作人、原因与重新购买时间 |
| record_visibility | 每个查看账户隐藏的记录编号与操作时间 |
| site_message | 账户通知、公告和问题反馈正文 |
| message_receipt | 每个账户的消息已读时间 |
| feedback_resolution | 管理员对反馈的处理决定、回复和更新时间 |

v1.3.0 的增量表由后端资源 `blockcoin-schema.sql` 创建，已有表和记录继续保留。资金规则和账户初始化方式见[字块币说明](../docs/blockcoin.md)。

v1.5.0 在同一增量脚本中增加 `game_play`，原 `game_record` 继续保存时长和游玩时间，两者通过记录编号对应。旧的手动记录与资金流水保留原值，自动记录由游戏会话更新。

v1.6.0 增加 `game_revocation`，后端启动时创建该表。管理员撤回游戏时保留原购买流水与余额；用户重新购买后，后端在原撤回记录中保存重新购买时间。管理员发放或收回字块币使用现有钱包和流水表，并按目标账户锁顺序处理。

v1.6.3 增加 `record_visibility`，隐藏操作只写入当前查看账户的显示选择。`game_record`、`game_play` 和字块币账本继续保留原数据，首页按完整记录计算次数、时长与游玩活动。个人与管理员记录列表共用隐藏标记，各账户的选择分别保存。

v1.8.1 增加 `site_message` 和 `message_receipt`。账户通知和公告正文共用消息表，每个账户使用独立回执保存已读状态。公告标题最多 80 个字符、正文最多 2000 个字符。账户事件通知与触发它们的资金、资料或游戏库修改在同一事务提交。

v1.9.0 在同一增量脚本中增加 `feedback_resolution`。用户反馈和公告共用 `site_message`，处理决定与管理员回复单独保存；原反馈编辑后会清除旧处理结果，并重新通知管理员。

新版本保留现有账号、密码、游戏与游玩记录。后端启动时会检查植物大战僵尸入口，并登记对应商品。

后端使用 `User` 统一表示管理员和游戏用户，账户合并后移除了 `Person`、`GameUser` 实体。游戏使用 `Game`，游玩记录使用 `GameRecord`。账户接口通过 `userId` 传递编号，地址沿用 `/api/gameUser`。前端的游戏库、收藏和商品资料维护共用 `views/game/GameList.vue`，账户页面位于 `views/account`。

`backups/before_user_merge.sql` 保存合并账户前的完整备份。开发者先通过 `merge_user.sql` 复制资料、切换外键，逐字段核对后，再执行 `finish_user_merge.sql` 删除旧表。当前数据库已经完成这两步。

备份中保留了一条原本未关联登录账号的个人资料，该资料仍按原状态保存。现有账号继续使用原编号、密码哈希和角色。

业务接口使用 POST，请求体为 `{"data": {...}}`，成功码为 `0`。登录接口直接在请求体最外层接收账号和密码。
